# 缓存、锁、多线程与循环调用

这是一份风险检查清单，不要求每个项目采用相同框架。所有结论必须结合实际读写路径、部署方式和业务一致性要求。

## 缓存和一致性

- key 是否包含必要的租户、模型、业务 ID、语言或权限范围；规范化规则是否一致，是否存在冲突和越权复用。
- 同一实体的主缓存、编号索引、关系集合和派生视图在新增、修改、删除、移动及 key 变化后是否同步；旧索引和空集合是否残留。
- 共享可变对象是否被调用方直接修改；使用并发 Map 不代表 value 对象或跨 key 操作线程安全。
- DB 提交与缓存更新/失效的时序是否匹配事务；回滚是否污染缓存，更新失败是否能恢复。
- 检查“读旧值 → 写线程提交并失效 → 读线程回填旧值”等具体交错；失效策略是否满足允许的陈旧时间，不能声称固定延迟双删必然一致。
- 全量刷新是否让读线程看见空缓存或半成品；刷新与增量事件竞争时是否丢更新。旧异步结果能否覆盖新版本。
- 多实例、本地缓存、Redis、事件传播间是否存在遗漏、乱序、重复或重连后的缺口。
- TTL、容量、负缓存、热点重建和失败回退是否有界；是否将热路径全量刷新当作修复一致性的办法。

## 锁

- 同一资源是否使用相同锁；锁对象是否稳定，锁范围能否覆盖实际临界区。
- check-then-act、多容器更新、读改写是否真正原子；仅有并发容器不能保护复合业务不变量。
- 多锁顺序、重入、升级及阻塞等待是否可能死锁；锁内 RPC/数据库/回调是否造成放大和反向调用。
- 仅在获得锁后释放，异常和中断路径是否释放；超时与中断是否被正确传播。
- 分布式锁是否按所有权释放，租约到期或暂停后旧持有者能否继续写；需要 fencing/version 校验时是否落实到资源端。
- 单 JVM 锁是否被误认为跨实例互斥；唯一约束、幂等或版本控制是否提供实际数据保护。不能把加锁当作所有场景的默认修复。

## 多线程与异步

- 共享字段、单例集合及其元素是否存在竞态、可见性或不安全发布；volatile 不保证复合更新原子。
- 线程池、队列、拒绝策略和并发数量是否有界；任务阻塞、嵌套提交及共享池是否造成饥饿。
- Future/CompletableFuture 的失败、取消和超时是否观察；调用返回后任务是否仍可能写入过期结果。
- ThreadLocal、MDC、租户、认证、语言和事务上下文是否正确传递并清理；线程复用是否串用户。
- 事务是否被误认为自动跨线程；异步任务是否早于提交读取数据。
- 关闭、重部署、重试和资源释放是否覆盖尚未完成的任务。并发测试应控制交错，不仅依赖 sleep 或单线程成功。

## 循环调用与规模

- 循环中的 SQL、RPC、Redis 和磁盘调用是否为 N+1；列明规模 N、每项调用数 k 及重试次数带来的上界。
- 是否有可用批量接口、合理分页、去重或有界并发；批量后权限、顺序、部分失败和事务语义是否保持。
- 嵌套循环、递归、依赖回调是否形成 O(N²)、环路、无限重试或重复刷新。
- 分页是否终止且顺序稳定，循环中数据变化是否导致重复或漏读。
- 并行流不等于解决 N+1；检查共享线程池、连接池和下游容量，不建议无界并发。
- 不因出现循环就报告性能缺陷：结合实际上限、查询计划、索引及调用证据判断。

## 发现的证据要求

每项包含：文件和行号、具体场景/执行交错、当前行为、预期或规则依据、影响、最小修复方向，以及可行的验证方式。缺乏部署拓扑、数据规模或一致性要求时列为待确认，不推断成必改。
