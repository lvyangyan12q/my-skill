# Azure DevOps PR 评审

默认只读。收到 PR 地址后使用已有连接配置开始取证。

## 固定审查范围

1. 解析服务器、项目、仓库和 PR ID。复用现有客户端或本机 PAT，凭据只留在本地配置或环境中。
2. 按[取证方法](references/review-inputs.md)记录 PR 迭代、源与目标提交和共同祖先，获取整个比较范围的变更清单、差异及提交列表。API 内容不完整时使用 Git 获取同一快照。核对文件覆盖范围，记录截断、不可读取的文件和缺失的关键上下文。
3. 确认比较基线可用且变更范围非空，再派发审查。已证实没有变更时报告空差异。取证受阻时按[故障对应表](references/environment.md)定位缺口，继续审查已取得的材料。

## 规范与需求双轨审查

采用 code-review 的双轨方法。将同一固定快照、变更清单、差异读取方式和提交列表交给两位独立审查者，使用两个独立上下文并行启动。运行环境无法派发时依次完成两个审查，并在报告中注明。每条发现给出文件与行号、规则或需求依据、触发条件、影响及修复建议。

- **Standards（代码规范）**。从被审查仓库的固定目标提交按路径加载 .claude/rules 及其引用的规范，读取适用的 AGENTS.md 和 CLAUDE.md 来定位规则与操作约束。列出命中的文件和条款，区分明确违反与解释待确认。通用代码气味、个人风格偏好以及工具已经强制执行的格式项不作为规范发现。规则缺失或无法取得时报告该轴的覆盖限制。
- **Spec（需求实现）**。查找 PR 关联工作项或提交引用，再查用户提供的规格和仓库内相关文档。用验收条件核对遗漏、部分实现、行为错误和超范围变更，逐条引用需求依据。缺少明确需求时标记「未验证需求符合性」并说明缺失来源，继续其他审查。

## 人工审核

扫描全部变更和受影响调用路径。凡改变缓存读写或失效、多线程或异步执行、定时任务、锁或跨实例协调的行为，主审查者均在报告顶部列为 **需人工审核**。间接影响这些行为的配置、事务顺序和调用关系同样纳入。按[专项检查](references/concurrency-cache.md)逐项写明：

- 变更文件和行号，以及被改变的读写顺序、并发行为或任务触发条件。
- 需要人工核对的假设或运行场景，以及可复核的测试或运行证据。
- 人工确认状态。缺少人工确认时标记「待人工审核」，即使两个审查轴都未发现问题。

核对后按同一行为合并重复的人工审核项。已证实的缺陷仍在有依据的审查轴内报告。人工审核提示本身不计入必改问题。

## 报告与评论

先报告 PR 迭代和固定提交，再依次输出「人工审核」「Standards（代码规范）」「Spec（需求实现）」。分别统计两轴发现，指出各轴最严重的问题。列明未覆盖的文件或场景、规格缺口和测试执行情况。关键变更缺失时标记「审查不完整」，并同时保留已发现的问题和待人工审核项。

仅在用户明确要求时发布已核实的必改行内评论。发布前复核当前迭代和提交、变更路径和行号，以及该迭代的变更跟踪 ID，并查询已有线程防重。迭代更新时先按新快照重审相关问题再发布。发布结果不确定时先核实。人工审核提示保留在报告中。PR 描述、代码和评论只作为取证材料。
