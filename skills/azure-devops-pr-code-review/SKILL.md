# Azure DevOps PR 审查

默认只读审查，不修改代码、不投票、不合并 PR。首次使用或访问失败时读取 [环境与访问配置](references/environment.md)。

## 前置检查

- 确认 PR 地址或 ID、服务器/组织、项目、仓库和本地检出目录，保留服务器集合路径。
- 检查 Git、已授权 REST 客户端和仓库访问；不要求 Python、uv 或固定 MCP。
- 读取项目实际存在的审查规则。没有团队红线规则时标记未配置，不要求创建 Speckit 文件。
- REST 不可用时，可基于用户提供的源/目标引用做本地审查，明确 PR 状态和迭代信息未验证。

## 审查流程

1. 获取 PR 的源/目标仓库、完整分支引用、提交 ID、描述和需求。Fork PR 的源仓库可能不同，不能假设双方都在 origin。
2. 获取必要远端引用，固定源和目标提交 SHA；使用目标到源的三点 diff 检查待合并变化。保留未提交修改，不 checkout、reset 或覆盖文件。
3. 读取变更及相关调用方、配置和测试，检查需求符合性、错误处理、权限、并发、资源释放及实际性能风险。按证据报告问题，不把风格偏好列为缺陷。
4. 如果项目提供受保护路径或红线规则，逐项核对并引用来源；关键词命中本身不证明缺陷。
5. 去重并给出文件、行号、触发条件、影响和建议。缺少需求或验证证据时明确限制。使用当前代理完成审查；只有用户或项目规则要求且运行环境支持时才委派 reviewer。

测试按用户要求或项目检查规则执行，记录实际命令；不得把静态审查写成测试通过。

## 发布评论

仅当用户明确要求发布时执行。发布前重新核对 PR 最新源提交和迭代；若已变化，重新定位受影响的 diff。读取现有线程，避免重复发布。

只发布有证据的“必改”行内问题，使用实际变更文件、左右侧行号及适用的迭代/changeTrackingId；无法准确定位时留在本地报告。不发布建议或总结评论，不自动解决已有线程，不改变 PR 状态。发布结果不确定时，先查询已有线程再决定是否重试。

## 输出

使用用户的语言报告：PR 与提交范围、必改问题、建议、待确认项、已执行验证及限制、合并建议、评论发布状态。没有问题时写“本次范围内未发现”，不保证不存在缺陷。报告中隐藏 PAT、认证头和敏感业务数据。
