# Karate API 测试

使用 Karate 的 .feature 文件作为请求和断言的唯一执行来源。首次使用、初始化或环境故障时读取 [运行环境与依赖](references/environment.md)。

## 执行前检查

确认接口需求、目标模块、基础 URL、认证来源和允许使用的测试环境。通过项目健康检查验证服务可用，不隐式启动或重启服务。

确认 JDK、构建工具、Karate/JUnit 版本、runner、配置和报告输出相互匹配。优先使用项目已有命令或 Maven Wrapper，不依赖指定路径的包装脚本。缺少基线时列出缺失项；只有用户要求初始化时才添加依赖、runner 和共享配置。

写入测试必须限定在用户授权的测试环境，明确测试数据归属和清理方式。不得默认操作生产数据、猜测账号 ID，或把测试失败视为授权修改业务代码。

## 编写测试

- 按业务能力组织 .feature，沿用项目资源目录；使用唯一用例标签，例如 @TEST-001。
- 公共 URL 和认证放入 karate-config.js 或 Background；敏感值从本机环境或安全配置读取，不写进版本库。
- 断言 HTTP 状态、响应字段、业务结果、权限和适用的无副作用条件，不只检查 200。
- 简短请求就地定义；复用或较大的数据放在同目录 JSON，并由场景实际读取，避免多份断言漂移。
- 测试数据使用每次运行唯一标记和响应生成的 ID。已有数据须经接口或受限查询确认，不默认 userId=1。
- 写入场景必须有失败时也执行的清理及清理结果验证；只清理本次创建的数据，不能清空共享表或环境。
- 先配置日志和报告脱敏，避免认证头、响应隐私数据进入 HTML、JUnit XML 和 CI 附件。

项目已有 tests.md 时可记录标签、前置条件、命令、数据来源和报告位置；不强制引入 Speckit 任务、证据哈希或阶段脚本。

## 数据库验证（按需）

纯 HTTP 场景不需要 MCP 或数据库访问。需要持久化证据时优先使用项目已有可重复运行的测试断言；也可使用已配置的 PostgreSQL MCP，只读检查目标表结构、测试数据和预期结果。

实际数据库角色必须限制为 SELECT，不能只依赖工具的只读说明。限定 schema/table、主键或运行标记、所需列及少量返回行；不全库扫描，不输出无关数据。记录查询条件、时间、预期和实际结果。

MCP 所需的 uv/uvx、Python、Node 或 Docker 由选定服务决定，见环境文档。缺少访问能力时仍可完成 HTTP 部分，但必须标明数据库验证未完成。临时 MCP 查询不能替代版本化的 CI 断言。

## 运行与判定

使用项目实际 runner 和最小标签。Maven 示例（替换 runner；Windows 用 mvnw.cmd）：

~~~sh
./mvnw test -Dtest=ApiTestRunner "-Dkarate.options=--tags @TEST-001"
~~~

确认 runner 接受该标签过滤。通过 Runner API 输出 JUnit XML 时，在匹配版本的 API 中显式启用 outputJunitXml(true)，不能假设默认产生。

通过标准：退出码为 0，本次报告包含选定用例且执行数大于 0，失败和错误为 0，所需数据库及清理验证完成。检查报告时间和场景标识，不使用旧报告或把零测试当作通过。

失败先区分产品缺陷、测试缺陷、数据缺失、环境故障和需求冲突；修复测试时保留业务断言。报告实际命令、执行用例、结果、报告路径和未验证项，不把接口成功等同于完整业务通过。
