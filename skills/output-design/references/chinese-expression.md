# 中文技术报告表达指南

适用于方案审阅稿、技术说明、风险分析及面向人的测试结论。内容范围、章节、必需字段和权威来源由当前任务及指定模板决定；本指南只处理**怎样表达**，不替代设计和审查。

借鉴 ASD-STE100 的术语一致、主体明确、条件靠近结果等清晰写法；ASD-STE100 的词典和语法规则面向英文。本指南不是它的中文译本，不代表正式符合该标准。英文或明确要求正式合规时，另读 [标准适用说明](asd-ste100.md)。

## 写之前：明确问题与事实

从当前任务确定读者需要判断的问题，提取事实、条件、结果、例外、数字、状态及来源；未知保持未知。章节与内容完整性遵循当前任务的写作要求，文字、表格、图示的选择和实际预览遵循 [output-design](../SKILL.md#实际执行路径)。本指南不另设结构调整规则。

## 写正文：一段只解决一个问题

1. 开头直接说已确认结论、对读者的影响和关键未知。说明“本轮做什么/不做什么”时，不把过程声明挤在业务结论前。
2. 句子写清**主体—动作—对象—条件—结果**；条件放在对应动作前或旁边。失败结果、旧数据和恢复方式跟着所属场景，不让读者到另一节拼接。
3. 专业名词首次出现时，沿已有定义解释其业务含义；同一对象保持同一名称。API、模型标签、字段、权限值、错误码和稳定 ID 原样保留，不自造同义词。
4. 长句按先后、因果或条件拆开。不要只删字数：拆分后保留“并且/或者”“仅当/如果”“可能/必须”的原有区别。步骤用真正的编号列表，一项一个主要动作；不用一行箭头或圈号代替完整流程。
5. 表格单元格放可比较的事实，不把多段说明压进单格。正文解释选择原因和用户可见后果；完整字段/接口定义按任务要求集中保留，避免正文与附录各写一遍。

### 技术报告中的改写示例

以下只演示**表达方式**，具体业务规则仍以当前需求和代码为准。

| 难读写法 | 清楚写法 | 不可丢掉的条件 |
|---|---|---|
| “补齐历史资料并隔离候选，默认不变。” | “查看旧记录时，按记录保存的用户 ID 补历史资料。新建或改选时，候选仍只取现存用户。” | 历史回显与新选人是两种用途，不能由“资料可查”推出“账号有效”。 |
| “若未提交/空值保留原值或清空。” | “未提交该字段时，按原更新契约处理。明确提交空值时，按该字段的可空规则处理。” | 未提交、`null`、空字符串不能合并成一种输入；原契约未知时标待核实。 |
| “补齐失败可降级，详情查无保留记录。” | “基础查询成功、历史补齐失败时，是否保留基础结果属于拟议规则。详情最终查无时是否保留业务记录，仍待确认。” | 基础失败、历史失败、正常查无必须区分；建议不写成已批准。 |

多条件适用时，把每个条件写在它所决定的动作旁；明确这些条件是同时满足还是任选其一。拟议结果用“拟”“建议”，已确认规则用“应”“仅”，不要用相同语气混写。

## 精确性：像可核对的技术手册，不伪称标准合规

- 范围：区分“所有”“本页”“本批”“指定 ID”；全量查询与按 ID 查询不能共用同一条结果限制。
- 数量：原样核对“至少/至多/超过”、单位、批量上限与分页位置；上限未知就标未知，不造数字。
- 状态：区分**已确认的业务决定**、**当前源码行为**、**拟议方案**、**待确认协议**与**真实测试结果**。对尚未验证的链路写出缺什么证据及影响，不用“已覆盖”概括。
- 否定：保留“不能作为候选”“不恢复权限”等边界，但同时写明正向用途，避免读者只看到一串禁令。
- 术语：“未观察到”“未执行”“失败”“不适用”各有不同证据含义；技术标识及来源保持可查。删除没有具体动作的修饰语，不删原条件或例外。
- 中文不套英文的词数上限或受控词典。短句、图表和手册式步骤都是手段，目标是让读者不跨多个段落就能解释同一场景。

## 交付前的表达检查

任选报告中一条正常路径和一条失败/旧数据路径，从读者角度回答：谁触发、输入是什么、按什么条件分支、谁负责处理、看到什么、原数据怎样保留或恢复？每个答案须能在同一场景及其就近定义找到；找不到就修改表达或指出源制品缺口。

再对照权威材料检查事实、范围、数量、否定、时间先后、确定程度和技术标识。这个检查只评价中文含义是否准确，不批准业务设计，也不证明读者已经实测理解；定义完整性与载体验证分别回到当前任务和 output-design。
