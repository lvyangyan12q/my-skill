# 为理解设计输出

把信息变成读者能理解、能检查的表达。借鉴 Karpathy 的思路，不局限于长文：为一个问题画图或制作一次性小网页，也可以是合理交付。支持文字、图示和交互 HTML。

## 输入与边界

从当前任务取得内容、读者要理解的问题和指定载体。任务要求决定写什么、必需章节和完整性；本技能决定怎样讲清楚，不新增业务规则、校验或审批决定。

保留事实、条件、例外、否定、数量、确定程度、技术标识及来源。缺口交当前任务处理，不用合理猜测补齐。示例、图示与模拟不构成真实执行证据。

指定格式/模板优先，保留机器字段与权威制品；允许附加阅读视图时从同一内容派生。不因优化表达改业务代码、启动 Speckit 或增加审查门禁。

## 实际执行路径

1. **找出理解障碍**：是语言含糊、关系难拼，还是需要比较变化？利用已有信息判断，不为排版重复访谈。
2. **选表达并制作**：按下表读取所需方法，产出实际文本、可渲染图或可打开页面，不只建议用户“可以画图”。简单结论直接用文字。
3. **核对语义与实际载体**：原含义是否保留，图是否读得懂，交互是否解释对应变化。不能预览时明确未验范围。
4. **交付**：给实际产物及必要使用方式。没有真实用户测试时，不宣称理解效果已实测提升。

| 障碍 / 输出 | 使用方法 | 具体交付 |
|---|---|---|
| 中文绕、碎、条件不清 | [中文表达方法](references/chinese-expression.md) | 自然连贯的改写，保留条件与未知 |
| 英文技术表达难读 | [英文表达方法](references/english-expression.md) | 清楚的英文，语气和技术含义不变 |
| 明确要求解释或严格采用 ASD-STE100 | [标准适用说明](references/asd-ste100.md) | 区分借鉴写法与正式合规要求 |
| 关系、分支、先后难拼接 | [图示制作方法](references/visual-explainers.md) 的图示部分 | 可呈现的流程/时序/结构/对照图 |
| 需要切换场景、逐步理解 | 同参考的场景讲解器部分；调用随附脚本 | 本地交互 HTML：切场景、走步骤、重置 |
| 需要改参数或观察计算/分支变化 | 同参考的自定义 HTML 部分 | 基于已有规则的小型解释工具 |

## ASD-STE100 怎样使用

默认借鉴清晰表达：术语一致、主体明确、动作直接、条件就近，一句一个主要意思。“约 80%”是 Karpathy 提到的宽松取向，不是合规分数。中文使用中文方法，不套英文词数与词典规则；英文按需使用正式标准。用户明确要求严格符合时才进入标准适用分支。

## 让表达真正起作用

- 文字解释含义；表格呈现对应；图示让关系可见；交互让读者探索变化。不是必须逐级生成四份文件。
- 关系复杂时主动考虑图示，需要比较变化时主动考虑 HTML，不能把长文换成卡片就算完成。
- 控件必须影响解释，图中连线必须有含义；装饰、折叠和动画数量不代表理解效果。
- 精确定义保留来源，关键前提与未知在相关位置可见。不能为了讲解顺畅隐藏限制，不能让视图变成另一套业务事实。
- 本地讲解器的能力是“呈现已给步骤”，不是自动业务分析、正式图布局引擎或任意计算器。超出适用范围按已有规则制作自定义视图。

完成时：原含义未变，读者需要理解的关系或变化被直接呈现，实际产物可用或未验范围明确，当前任务要求仍保留。
